# Project Kit — дизайн первой версии

Дата: 2026-10-01. Статус: одобрено пользователем; дополнено требованием к ёмкости промптов.

Этот документ описывает предполагаемый результат. Продуктовые файлы, внешние зависимости и настройки агентов ещё не созданы. Следующий этап — review отдельного плана реализации. Пользователь отдельно поручил создать новый репозиторий.

## 1. Назначение и согласованные условия

Project Kit — версионируемый набор для запуска и дальнейшего ведения проектов с AI. Сначала им пользуется один разработчик, впоследствии к тому же процессу может присоединиться команда.

Пользователь определил следующие условия:

- Тип проекта и технический стек заранее неизвестны; набор помогает выбрать их из требований.
- Поддерживается весь цикл: запуск, проектирование, реализация, проверка, выпуск и развитие.
- Обязательные агенты первой версии — Codex и Claude Code.
- Внешние skills используются в исходном виде. Можно добавлять новые внешние наборы и собственные skills.
- Общая основа и её зависимости версионируются; существующие проекты обновляются явно.
- Процесс должен оставаться компактным, а правила — понятными будущим участникам.
- Промпты должны быть максимально ёмкими: передавать суть и сохранять ключевые условия проекта.
- В результате проектирования показываются структуры файлов набора и создаваемого проекта.

Успешный результат: из описания задачи получается рабочая основа проекта с зафиксированными решениями и проверяемыми командами. Смена агента или подключение человека сохраняет методологию и актуальный контекст.

## 2. Архитектура и границы

Один репозиторий объединяет шесть частей:

| Часть | Ответственность | Зависимости |
| --- | --- | --- |
| core | Общие правила разработки, Git, качества и контекста | Не зависит от стека проекта |
| skills | Собственные сценарии запуска, проверки и обновления | core, выбранный профиль, вспомогательные команды |
| upstream | Исходные внешние репозитории на конкретных commits | Git и доступ к выбранным источникам |
| profiles | Состав набора, роли workflows и настройки интеграций | Идентификаторы доступных наборов и адаптеров |
| adapters | Подключение и проверка возможностей конкретного агента | Профиль, закреплённые исходники, версия клиента |
| templates | Начальные документы и файлы конфигурации проекта | Результаты проектирования и профиль |

Набор поставляет методологию, инструкции и небольшие вспомогательные команды. Техническую основу нового продукта создают подходящие инструменты выбранного стека. Большой каталог готовых приложений не является условием готовности v1.

Продуктовая разработка остаётся в репозитории продукта. Project Kit не вводит отдельный трекер задач, собственный агентный runtime или обязательный инфраструктурный стек.

## 4. Структура создаваемого проекта

Общая часть одинакова по назначению. Ниже показан вариант с каталогами src/tests и GitHub Actions; техническая структура и CI адаптируются к выбранному стеку и месту размещения репозитория.

~~~text
new-project/
├── README.md
├── AGENTS.md
├── CLAUDE.md
├── .gitignore
├── project-kit.yaml              # Настройки, которыми владеет проект
├── project-kit.lock.yaml         # Точная применённая версия набора
├── .project-kit/
│   └── core/                     # Управляемый снимок общих правил
│       ├── entry.md
│       ├── workflow.md
│       ├── git.md
│       ├── context-policy.md
│       └── quality.md
├── .codex/
│   └── config.toml               # Проектная конфигурация адаптера
├── .claude/
│   └── settings.json             # Проектная конфигурация адаптера
├── docs/
│   ├── project.md
│   ├── architecture.md
│   ├── development.md
│   └── decisions/
│       └── 0001-stack.md
├── .github/
│   └── workflows/
│       └── checks.yml

~~~

Плагины устанавливаются средствами адаптеров; их кеши не входят в Git продукта. Репозиторий продукта хранит ссылку на точный commit Project Kit. Из этого commit восстанавливаются версии upstream через Git submodules. Встраивать полное дерево набора и всех его зависимостей в каждый продукт не требуется.

AGENTS.md содержит короткие обязательные правила, указание прочитать .project-kit/core/entry.md и маршрут к проектным документам. CLAUDE.md импортирует AGENTS.md через @AGENTS.md и содержит только дополнительные инструкции для Claude Code. Подробные материалы открываются по текущей задаче.

## 5. Методология по умолчанию

| Область | Правило и результат |
| --- | --- |
| Цель | docs/project.md фиксирует пользователей, назначение, границы, ограничения и критерии успеха |
| Проектирование | Существенные решения сохраняются вместе с рассмотренными вариантами, причинами и последствиями |
| Стек | Выбор следует из требований; оцениваются разработка, эксплуатация, стоимость изменения и компетенции участников |
| Задачи | Один выбранный источник задач, указанный в docs/development.md; у задачи есть ожидаемый результат и критерии приёмки |
| Git | Рабочая основная ветка, короткие ветки задач, проверяемые изменения через PR; worktrees применяются при параллельной работе |
| Качество | Проверки соответствуют изменению; завершение подтверждается наблюдаемыми результатами |
| Контекст | Разделяются актуальные правила, предложения, принятые решения и результаты операций |
| Автономность | Агент доводит согласованную задачу до результата; изменение цели и существенные компромиссы обсуждаются |

Масштаб процесса:

- Исследование: вопрос, ограниченный эксперимент, вывод с основаниями.
- Небольшое изменение: короткое описание решения, реализация, проверка.
- Новая подсистема или существенное изменение: требования, варианты, согласованный дизайн, план, реализация, проверка.

Для каждого этапа профиль выбирает основной workflow. Требования внешнего skill учитываются до его включения: общий маршрут не обещает обходить его обязательные этапы. Конфликтующие процессы не разрешаются произвольным порядком загрузки.

Профиль может уточнять общие значения по умолчанию для проекта. Правила среды исполнения и явные инструкции пользователя сохраняют свой действительный приоритет; репозиторные документы не объявляются системными промптами более высокого уровня.

## 6. Контекст и взаимодействие агентов

### 6.1. Ёмкость промптов

Краткость оценивается вместе с полнотой. Сохраняются цель, границы, существенные ограничения, принятые решения, условия завершения и маршрут к актуальным источникам. Инструкция, после сокращения допускающая разные несовместимые действия, считается неполной.

Одно правило имеет одну каноническую формулировку. Стартовые инструкции содержат обязательные действия и ссылки по типу задачи; подробности, примеры и обоснования открываются по необходимости. Собственный skill описывает вход, действие, результат и проверку; пересказ внешнего skill не добавляется.

Ориентир для наших стартовых инструкций AGENTS.md + core/entry.md — до 400 слов суммарно; для тела собственного SKILL.md — до 250 слов. Это порог для review, а не команда обрезать текст. Превышение сопровождается объяснением, какие обязательные сведения требуют дополнительного объёма. Контекст продукта остаётся доступным через прямые ссылки независимо от размера инструкций.

Бюджет относится к нашим инструкциям. Объём метаданных внешних skills учитывается отдельно; их исходное содержимое сохраняется. Избыточный контекст уменьшается выбором профиля и поддерживаемых способов подключения.

### 6.2. Общие источники и адаптеры

Общий контекст хранится один раз. core/entry.md содержит только постоянно нужные правила и ссылки; workflows, Git и качество читаются по применимости. Архивы, полные логи и все внешние skills не загружаются при каждом старте.

Собственные skills оформляются в формате Agent Skills и включают необходимые ресурсы. Их инструкции определяют вход, последовательность действий, результат и условие завершения. Особенности команд и инструментов конкретного агента описываются в адаптере.

При смене агента в текущей задаче остаются ссылки на изменения, принятые решения, выполненные проверки и оставшаяся работа. Содержимое чата не служит единственным носителем состояния. Второй список задач в документации набора не создаётся.

Адаптер должен определить доступные возможности клиента, установить требуемые наборы, применить поддерживаемые настройки и проверить результат. Версия клиента и способ запуска включаются в отчёт совместимости. Заявленная поддержка агента подтверждается отдельной проверкой; наличие подходящего файла манифеста само по себе недостаточно.

Установка и обновление для одного проекта сохраняют настройки других проектов и активных сессий. Если выбранный способ подключения не обеспечивает требуемое разделение версий, адаптер сообщает о несовместимости этого способа.

Hooks и MCP подключаются по профилю с учётом возможностей агента. Их настройки хранятся отдельно от переносимого текста правил. Настройки авторизации и секреты остаются в предусмотренных клиентом локальных механизмах.

## 7. Версии, профили и владение

### 7.1. Внешние зависимости

Каждый внешний репозиторий хранится в upstream как submodule на точном commit. .gitmodules содержит источник и путь; закреплённый SHA хранится в дереве Git. В профиле эти SHA не дублируются.

Тег внешнего релиза удобен для человека, но основанием воспроизведения служит commit. Использование плавающего main или latest не считается закреплением версии. Внешние исходники сохраняются без локальных правок.

Добавление источника и включение его в рабочий профиль — разные изменения. Добавление требует определения источника и commit; включение — определения роли, необходимых возможностей и проверки совместимости.

Единица подключения по умолчанию — готовый пакет или плагин. Выбор отдельных skills применяется, когда штатная поставка и адаптер это поддерживают с сохранением всех необходимых ресурсов. Наличие исходников не означает возможность произвольно вырезать из пакета отдельные SKILL.md.

### 7.2. Настройки проекта

project-kit.yaml содержит версию схемы, выбранный профиль, целевых агентов и проектные настройки профиля. Это редактируемая конфигурация намерения. Факты о продукте и обоснования решений остаются в проектной документации.

project-kit.lock.yaml содержит версию схемы, источник и точный commit набора, хеш разрешённой конфигурации, идентичность подготовленных пакетов и базовые хеши управляемых файлов. Это запись применённого состояния, обновляемая командами набора.

Список upstream commits выводится из закреплённого Project Kit, а не поддерживается вторым списком вручную. Если установка формирует пакет из исходников, фиксируется также хеш его содержимого. Совпадение отображаемого номера версии без проверки происхождения или содержимого недостаточно.

Кеши исходников и подготовленных пакетов адресуются по закреплённой версии и содержимому. Совместно используемые исходники остаются неизменяемыми. Фактическая активная установка каждого агента проверяется отдельно: другой глобально установленный релиз не принимается за нужную версию.

### 7.3. Владение файлами

| Категория | Файлы | Правило обновления |
| --- | --- | --- |
| Управляемые | .project-kit/core и lock-файл | Обновляются инструментом; обнаруженные локальные правки требуют разбора |
| Проектные | Код, README, docs/project.md, архитектура, решения, development.md, project-kit.yaml | Создаются при запуске, затем развиваются в проекте; обновление набора их не заменяет |
| Смешанные | AGENTS.md, CLAUDE.md, конфигурации агентов | Изменяются только принадлежащие набору блоки или ключи; остальные части сохраняются |
| Технические | Сборка, зависимости приложения, CI | Принадлежат продукту после создания; последующие изменения оформляются как задачи продукта |

Набор выпускается тегами с changelog. Несовместимое изменение схемы, правил обновления или обязательного поведения требует major-версии; совместимые дополнения — minor; исправления без изменения обязательств — patch. Изменение стороннего набора оценивается по его влиянию на комплект.

## 8. Основные операции

### 8.1. project-init

Вход: описание задачи, целевая директория, исходные ограничения и выбранная версия набора.

1. Skill уточняет назначение, пользователей, критерии успеха и ограничения.
2. Сравнивает подходящие стеки, фиксирует решение и проходит необходимые этапы выбранного workflow.
3. Формирует профиль и проектные документы из принятых решений.
4. Вспомогательная команда создаёт согласованные файлы и подключает агентов через адаптеры.
5. Средствами выбранного стека создаётся техническая основа; сохраняются команды и версии генераторов.
6. Выполняются проверки запуска и настройки; результат включает дерево фактически созданных файлов.

Выход: репозиторий с документацией, технической основой, командами разработки и проверенной конфигурацией обоих агентов. Bootstrap не предполагает публикацию продукта или развёртывание рабочего сервиса.

Интерактивный выбор и проектирование выполняет skill; команды файловых операций принимают уже определённые параметры. Повторный запуск на той же конфигурации сохраняет дополнения и не создаёт дубликатов.

### 8.2. project-check

Вход: корень проекта и его конфигурация. Проверка по умолчанию не изменяет проект.

Проверяются схемы настроек, закреплённая версия, управляемые файлы, ссылки на контекст, согласованность профиля, обнаружение собственных и внешних skills и фактическая конфигурация агентов. Проверка отдельно показывает, какие наблюдения выполнены по файлам, а какие подтверждены работающим клиентом.

Выход: структурированный отчёт и краткое объяснение. Статусы: ready, incomplete, incompatible, drift. Только ready означает, что обязательные проверки выбранного профиля пройдены; пропущенная runtime-проверка остаётся incomplete.

Статус записывается для каждой проверки. Общий статус выбирается в порядке incompatible, drift, incomplete, ready; успешный код завершения возвращается только для ready.

### 8.3. project-upgrade

Вход: проект и явно выбранная новая версия набора.

1. Проверяет исходное состояние и доступность текущей и целевой версий.
2. Создаёт отдельную ветку для обновления, сохраняя пользовательскую работу.
3. Готовит новые управляемые файлы и настройки, показывает diff и изменения workflows.
4. Разбирает пересечения с локальными дополнениями без молчаливой перезаписи.
5. Проверяет результирующий профиль и установки агентов.
6. Записывает новый lock только для завершённого согласованного состояния и формирует материал для review.

Обновление исходников не объявляется завершённым обновлением активного runtime. Установка или активация новой версии согласуется с областью текущей операции и доступными средствами клиента.

## 9. Ошибки и восстановление

| Ситуация | Поведение |
| --- | --- |
| В директории уже есть конфликтующие файлы | Сохранить их, показать список пересечений; продолжать только после разрешения конкретного конфликта |
| Недоступен источник или закреплённый commit | Остановить зависимый шаг, сохранить прежнее применённое состояние |
| Версия клиента не поддерживает нужную возможность | Показать incompatibility; не заменять её молча другим workflow |
| Активный плагин отличается от закреплённого | Показать drift и различие между требуемым и фактическим состояниями |
| Ошибка генератора, установки или проверки | Сохранить результат завершённых шагов и указать точную команду продолжения |
| Локально изменён управляемый файл | Подготовить сравнение базового, локального и нового содержимого; не стирать изменение |
| Рабочее дерево содержит чужие изменения | Сохранить их; обновление выполняется только в подходящем изолированном состоянии |

Lock записывается атомарно после успешного завершения относящегося к нему этапа. Частичный результат не маркируется как ready. Проверка готовности повторяется после перезапуска клиента, если новые настройки требуют новой сессии.

## 10. Проверка готовности v1

Два независимых сценария используют небольшие проекты разных типов и стеков: CLI и веб-API. Сценарии проверяют поведение набора, а не обещают поддержку только этих типов приложений.

Критерии приёмки:

1. Из описания каждого проекта получаются заполненные документы, выбранный стек с обоснованием и работоспособная техническая основа.
2. Команды запуска и проверки выполняются из нового checkout по сохранённым инструкциям.
3. Codex и Claude Code получают общие правила, обнаруживают нужные skills и используют ожидаемые версии в каждой заявленной среде запуска.
4. Повторная настройка не меняет результат без изменения входов и сохраняет пользовательские настройки.
5. Обновление набора после изменений README, проектных решений и собственных дополнений сохраняет эти изменения.
6. Подготовленный конфликт управляемого файла обнаруживается и оставляет исходное содержимое доступным для разбора.
7. Несовпадение runtime-версии, отсутствующая зависимость и несовместимый профиль не дают статус ready.
8. Во всех отчётах различаются запланированные, созданные и фактически проверенные файлы и возможности.
9. Два проекта с разными закреплёнными версиями набора сохраняют свои активные конфигурации при настройке и обновлении одного из них.
10. В наших промптах сохранены ключевые условия проекта, правила не дублируются, ссылки разрешаются; превышение ориентиров объёма объяснено. Короткий, но неполный промпт проверку не проходит.

Обязательные автоматические проверки: схемы и ссылки; корректность submodule pins и профиля; повторный запуск; сохранение проектных файлов при обновлении; выявление конфликтов и drift. Проверка работы агентов проводится на тех клиентах, которые заявлены в совместимости релиза, и сохраняет краткое evidence.

Модели и внешние сервисы могут менять поведение независимо от версии исходников. Поэтому воспроизводимость состава инструкций и пакетов отделяется от проверки фактического поведения на выбранных сценариях.

## 11. Основания технических решений

- Git submodules сохраняют отдельную историю и фиксируют commit зависимости: [Git documentation](https://git-scm.com/docs/gitsubmodules).
- Формат SKILL.md и загрузка ресурсов по необходимости: [Agent Skills specification](https://agentskills.io/specification).
- Codex читает AGENTS.md как проектные инструкции: [Codex instructions](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
- Проектная конфигурация Codex располагается в .codex/config.toml и зависит от доверия к проекту: [Codex configuration](https://learn.chatgpt.com/docs/config-file/config-basic).
- CLAUDE.md может явно импортировать AGENTS.md: [Claude Code memory](https://code.claude.com/docs/en/memory#share-one-file-with-other-coding-tools).
- Claude Code дополняет переносимый формат skills собственными возможностями: [Claude Code skills](https://code.claude.com/docs/en/skills).

Документация проверена при подготовке дизайна. Совместимость конкретных версий клиентов и пакетов подтверждается при реализации и выпуске; установленные здесь версии сами по себе не являются выбором зависимостей будущего релиза.
